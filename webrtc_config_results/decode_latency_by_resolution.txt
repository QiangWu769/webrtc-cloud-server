关键发现
===============================================================================

1. **分辨率与解码延迟的关系**

   解码延迟随分辨率增加呈显著上升趋势:

   - 640x360   (低分辨率):  1.74 ms/帧  ← 基准
   - 960x540   (中等偏低):  2.00 ms/帧  (↑ 15%)
   - 1280x720  (高清):     13.22 ms/帧  (↑ 660%)
   - 1920x1080 (全高清):   13.79 ms/帧  (↑ 693%)

   **关键转折点**: 从 960x540 到 1280x720，解码延迟激增 6.6倍

2. **分辨率档位分析**

   低分辨率档 (≤960x540):
   - 平均解码延迟: 1.74 - 2.00 ms/帧
   - 适用场景: 网络条件差、移动设备、低功耗需求
   - 优势: 极低延迟，实时性好

   高分辨率档 (≥1280x720):
   - 平均解码延迟: 13.22 - 13.79 ms/帧
   - 适用场景: 桌面应用、高清会议、优质网络
   - 特点: 延迟相对稳定，720p 与 1080p 差异仅 4.3%

3. **最大解码延迟 (max_decode_ms)**

   - 低分辨率 (640x360, 960x540): 3 ms
   - 高分辨率 (1280x720, 1920x1080): 28 ms

   高分辨率最大延迟是低分辨率的 9.3 倍，说明高分辨率解码存在
   偶发的性能瓶颈，可能与:
   - I帧/关键帧解码
   - CPU负载峰值
   - 内存带宽限制

4. **主要传输分辨率**

   从解码帧数来看，本次传输主要使用两个分辨率:

   - 1280x720:  3559 帧 (主要分辨率，占比最高)
   - 1920x1080: 2991 帧 (次要分辨率)
   - 640x360:    438 帧 (初始探测/网络波动)
   - 960x540:    570 帧 (过渡阶段)

   这表明 WebRTC 的自适应码率控制在传输过程中根据网络状况
   在 720p 和 1080p 之间动态切换。

5. **decode_ms vs 实际平均延迟**

   WebRTC stats 中的 decode_ms 是瞬时采样值，而实际平均延迟
   (totalDecodeTime / framesDecoded) 更能反映整体性能:

   分辨率        decode_ms    实际平均     差异
   --------------------------------------------------------
   1280x720         8.5 ms      13.22 ms    +55.5%
   1920x1080       17.4 ms      13.79 ms    -20.7%

   这说明 decode_ms 采样存在波动，实际平均值更稳定可靠。

===============================================================================
性能瓶颈分析
===============================================================================

1. **解码延迟构成** (以 1280x720 为例)

   - 平均解码时间: 13.22 ms/帧
   - 目标帧率: 30 fps (33.33 ms/帧)
   - 解码时间占比: 39.7% (13.22/33.33)

   解码占用了近 40% 的帧时间预算，这在实时传输中是合理的。

2. **720p vs 1080p 解码性能**

   - 像素数差异: 1080p 是 720p 的 2.25 倍 (1920×1080 / 1280×720)
   - 解码延迟差异: 1080p 仅比 720p 高 4.3% (13.79 vs 13.22)

   **结论**: VP8 解码器在处理 1080p 时效率很高，延迟增长远低于
   像素数增长比例。这可能归功于:
   - 硬件加速
   - 并行解码优化
   - SIMD 指令集优化

3. **分辨率切换开销**

   传输过程中多次在不同分辨率间切换 (640→960→1280→1920)，
   但 max_decode_ms 仅为 28 ms，说明 VP8 解码器能够快速适应
   分辨率变化，切换开销较小。

===============================================================================
实际应用建议
===============================================================================

1. **低延迟场景** (游戏、实时互动)
   - 推荐分辨率: 640x360 或 960x540
   - 预期延迟: < 2 ms/帧
   - 总延迟预算: 编码+传输+解码 < 100 ms

2. **标准视频会议** (Zoom, Teams 类应用)
   - 推荐分辨率: 1280x720
   - 预期延迟: ~13 ms/帧
   - 平衡点: 清晰度与实时性的最佳折衷

3. **高清内容分享** (屏幕共享、演示)
   - 可选分辨率: 1920x1080
   - 预期延迟: ~14 ms/帧
   - 优势: 相比720p延迟仅增加1ms，但清晰度提升显著

4. **自适应策略优化**
   - 建议在 720p 和 1080p 之间切换(延迟差异小)
   - 避免频繁降至 640x360(用户体验差)
   - 网络恢复后优先升至 720p(性价比最高)

===============================================================================
技术细节
===============================================================================

数据提取方法:
  - 源文件: receiver_cloud.log
  - 关键字段: VideoReceiveStreamInterface stats
  - 提取参数: frameWidth, frameHeight, framesDecoded, decode_ms,
               max_decode_ms, totalDecodeTime
  - 统计方法: 按分辨率分组，计算 totalDecodeTime/framesDecoded

计算公式:
  实际平均解码延迟 = totalDecodeTime / framesDecoded × 1000 (ms/帧)

采样频率:
  - 640x360:  14 次采样
  - 960x540:   4 次采样
  - 1280x720: 25 次采样
  - 1920x1080: 68 次采样 (最高)

===============================================================================
总结
===============================================================================

1. VP8 解码延迟随分辨率增长呈两段式分布:
   - 低分辨率段 (≤960x540): 1.7-2.0 ms/帧
   - 高分辨率段 (≥1280x720): 13.2-13.8 ms/帧

2. 1280x720 是性价比最优选择:
   - 延迟仅 13.22 ms/帧 (占帧时间 40%)
   - 相比 1080p 延迟几乎相同，但像素减少 56%
   - 占本次传输解码帧数最多 (3559 帧)

3. VP8 解码器在高分辨率下表现优异:
   - 720p→1080p 像素增加 2.25 倍，延迟仅增 4.3%
   - 最大解码延迟控制在 28 ms 以内
   - 分辨率切换开销低，适合自适应传输

4. 实时性能评估:
   - 所有分辨率解码延迟 < 15 ms/帧
   - 满足 30fps 实时传输要求 (33.33 ms/帧)
   - 适合视频会议、直播等实时应用场景
